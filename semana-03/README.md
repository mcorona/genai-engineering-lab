# Week 3: adaptation — to fine-tune or not to fine-tune?

> Spanish names (folders, files, JSON keys, flags, stack names, status values) are explained in the [glossary](../docs/glossary.md). The documentation is in English.

Task: translate a question in Spanish into SQL over the LegacyBridge legacy schema (PostgreSQL 16), and determine whether fine-tuning a model (LoRA) is worth it or whether prompting or RAG is enough.

**Decision rule:** if prompting or RAG is enough, do not fine-tune. Document the decision.

**Decision:** do not fine-tune. With the 27B model, the rules in the prompt are enough. See [Decision](#decision).

## Data

- 229 candidates generated from 19 templates over the legacy schema (`generar_pares.py`).
- 220 accepted: each SQL statement is executed in PostgreSQL with the `lb_reader` role, in a read-only transaction with a 5 s `statement_timeout`.
- 9 rejected because of an execution error (`data/rechazados.jsonl`).
- 0 overlaps with the LegacyBridge gold set (`evals/golden_set.yaml` in the LegacyBridge repository, 80 cases, read-only). Those cases are excluded from the pairs.
- An 80/20 split by template with seed 42: **174 training pairs** (`data/pares_train.jsonl`) and **46 evaluation pairs** (`data/pares_eval.jsonl`). The evaluation set never enters training.
- LoRA training: 157 training pairs and 17 validation pairs (`data/lora/`), generated by `preparar_lora.py`.

The business rules that the model must apply are in `reglas_legado.md` (in Spanish, since it is part of the prompt). They are 12 rules taken from `docs/legacy-defects.md` in the LegacyBridge repository: current records, amounts stored as text, CHAR(8) dates, currency and agent, invoice lines, active customers and products, current stock, cost with a decimal comma, and stock movements.

## Methods

| Method | Model | Configuration |
|---|---|---|
| 27B base | Qwen3.8-27B MLX 4-bit (LM Studio) | temperature 0, reasoning allowed, `max_tokens` 8192, only `content` is used |
| 7B base | Qwen2.5-Coder-7B-Instruct MLX 4-bit | temperature 0, `max_tokens` 8192 |
| 7B + LoRA v1 | Qwen2.5-Coder-7B + adapter | mlx-lm, LoRA, 16 layers, lr 1e-5, batch 2, 300 iterations, `--mask-prompt`, maximum length 2048 |
| 7B + rules in the prompt | Qwen2.5-Coder-7B | all 12 rules in the system prompt (`--reglas`) |
| 27B + rules in the prompt | Qwen3.8-27B | temperature 0, `max_tokens` 8192, all 12 rules in the prompt (`--reglas`) |
| 27B + RAG-lite | Qwen3.8-27B | temperature 0, `max_tokens` 8192, only the rules relevant to each question (`--rag`, `rag_reglas.py`) |

The LoRA run with lr 1e-4 diverged to NaN from about iteration 40. It was discarded and retrained with lr 1e-5, which converged (validation loss 0.007).

## Metrics

- **Executes:** the query runs in PostgreSQL without an error.
- **Result match:** the returned rows equal those of the reference. Order is ignored, and the comparison normalizes amounts with `$` and commas, decimal commas, and codes with leading zeros treated as text. This is the primary metric.
- **SQL exact match:** reported, but very low (0 to 9%) because many queries are equivalent. It is not used for the decision.
- **Confidence interval:** 95% Wilson interval (`estadistica.py`).
- **Paired comparison:** exact McNemar test on the same 46 pairs.

## Results

Evaluation set: 46 pairs. Primary metric: result match.

| Method | Executes | Result match [95% CI] |
|---|---|---|
| Qwen3.8-27B base | 73.9% | 45.7% [32.2, 59.8] |
| Qwen3.8-27B + rules in the prompt | 69.6% | **50.0%** [36.1, 63.9] |
| Qwen3.8-27B + RAG-lite | 58.7% | 41.3% [28.3, 55.7] |
| Qwen2.5-Coder-7B base | 80.4% | 37.0% [24.5, 51.4] |
| Qwen2.5-Coder-7B + LoRA v1 | 84.8% | 37.0% [24.5, 51.4] |
| Qwen2.5-Coder-7B + rules in the prompt | 54.3% | 28.3% [17.3, 42.5] |

Paired tests (McNemar, result match):

- 7B base vs. 7B + LoRA v1: both get exactly the same cases right (0 discordant pairs), p = 1.000. The LoRA does not change the result match.
- 27B base vs. 27B + rules in the prompt: 5 cases only the base gets right, 7 only the rules variant gets right, p = 0.774. Not significant.
- 27B base vs. 27B + RAG-lite: 7 cases only the base, 5 only RAG, p = 0.774. Not significant.
- 27B + rules vs. 27B + RAG-lite: 7 cases only the rules variant, 3 only RAG, p = 0.344. Not significant.
- 27B base vs. 7B base: 5 cases only the 27B gets right and 1 only the 7B, p = 0.219. Not significant.

## Before and after

The same 46 evaluation pairs and the same metric. Each change is measured against the baseline of the same model.

**Fine-tuning (LoRA), on the 7B model**

| Metric | Before: 7B base | After: 7B + LoRA v1 | Change |
|---|---|---|---|
| Executes | 80.4% (37/46) | 84.8% (39/46) | +2 cases |
| Result match | 37.0% (17/46) | 37.0% (17/46) | 0 |
| Exact match (SQL) | 0.0% | 0.0% | 0 |

The model gets the same 17 cases right before and after (McNemar p = 1.000). Fine-tuning changes the syntax, not the result.

**Prompt with rules, on the 27B model**

| Metric | Before: 27B base | After: 27B + rules | Change |
|---|---|---|---|
| Executes | 73.9% (34/46) | 69.6% (32/46) | −2 cases |
| Result match | 45.7% (21/46) | 50.0% (23/46) | +2 cases |
| Exact match (SQL) | 0.0% | 0.0% | 0 |

The change is not significant (McNemar p = 0.774). The rules improve the result without improving the syntax.

**RAG-lite, on the 27B model** (for reference; not adopted)

| Metric | Before: 27B base | After: 27B + RAG-lite | Change |
|---|---|---|---|
| Executes | 73.9% (34/46) | 58.7% (27/46) | −7 cases |
| Result match | 45.7% (21/46) | 41.3% (19/46) | −2 cases |
| Exact match (SQL) | 0.0% | 6.5% (3/46) | +3 cases |

Exact match rises only with RAG, but the result match drops: a sign that the model writes different SQL without getting the content right. Not adopted.

**Reference: 7B with the rules in the prompt**

| Metric | Before: 7B base | After: 7B + rules | Change |
|---|---|---|---|
| Executes | 80.4% (37/46) | 54.3% (25/46) | −12 cases |
| Result match | 37.0% (17/46) | 28.3% (13/46) | −4 cases |
| Exact match (SQL) | 0.0% | 8.7% (4/46) | +4 cases |

A long prompt confuses the 7B model: it copies SQL fragments from the rules, which shows in both execution and result match.

## Reading the results

- **LoRA v1 learns the format, not the rules.** It executes more often (80.4% to 84.8%) but gets exactly the same cases right as the base model.
- **The rules in the prompt make the 7B model worse.** Only 54% of its queries execute: it copies SQL fragments from the rules (for example `COUNT(DISTINCT ON ...)`) and invents columns. A long prompt with fragments confuses this model.
- **The 27B model with the rules in the prompt is the best method measured** (50.0%), but its difference from the 27B base (45.7%) is not significant.
- **RAG-lite does not improve on the base** (41.3%). Selecting rules by keyword loses context that the model does use when it receives all of them.
- **The rules in the prompt help the 27B model and hurt the 7B model.** The large model uses them; the small one copies SQL fragments and makes mistakes.

## Decision

**Do not fine-tune.** For this schema and this model, the prompt is enough.

- The 27B model with all the rules in the prompt matches and slightly exceeds the base (50.0% vs. 45.7%). No difference is significant, but the prompt does not make the result worse.
- LoRA v1 does not improve the result match on the 7B model: it gets the same cases right as the 7B base.
- RAG-lite is not enough: it falls below the full rules (p = 0.344) and does not improve on the base.

Limitation of the comparison: fine-tuning was tested on the 7B model, not on the 27B model. With 46 pairs there is no power to detect differences of 5 to 10 points. The conclusion is that there is no evidence that fine-tuning helps, and that prompting the large model reaches the base level without training anything.

Recommended method for this case: the 27B model with the rules in the prompt (`--reglas`).

## Limitations

- **Data overlap.** Training and evaluation share customers, invoices and items. The test measures applying rules to known records, not generalizing to new records.
- **Small sample.** With n = 46, the intervals are about ±14 points wide. Differences of 1 to 3 cases are not evidence.
- **Strict metric.** Extra columns (for example `clave`) and top-1 vs. a ranking count as failures. The numeric normalization did not change any result (`--reevaluar`), so the failures are about content, not format.
- **Exact match is not informative** for equivalent SQL.
- **27B reasoning.** If the model uses up the 8192 tokens without producing SQL, it counts as a failure. Check `finish_reason` in `resultados/*_detalle.jsonl`.
- **Discarded runs, kept for traceability:**
  - `sin_razonamiento_roto_base_*`: a run with `/no_think` and 1024 tokens. 28 of 46 cases produced no SQL. Discarded.
  - `prueba_*`: tests with 3 pairs. They are in `.gitignore`.

## How to run it

It needs LM Studio at `http://localhost:1234/v1` with the 27B model loaded, the LegacyBridge database running (`legacybridge2-db`), and `~/legacybridge-v2/.env` with `LB_READER_PASSWORD` (from the LegacyBridge repository).

```bash
# from the repository root
set -a; source ~/legacybridge-v2/.env; set +a

# 27B runs
uv run python semana-03/evaluar_sql.py --nombre base27b_reglas --reglas
uv run python semana-03/evaluar_sql.py --nombre base27b_rag --rag

# Intervals and the paired comparison
uv run python semana-03/estadistica.py base base27b_reglas base27b_rag --comparar base base27b_reglas
```

For the 7B model with LoRA, start the server with the adapter on another port:

```bash
mlx_lm.server --model $HOME/.lmstudio/models/lmstudio-community/Qwen2.5-Coder-7B-Instruct-MLX-4bit \
  --adapter-path semana-03/adapters/qwen7b-sql --port 8081
uv run python semana-03/evaluar_sql.py --nombre lora7b --base-url http://localhost:8081/v1 \
  --modelo "$HOME/.lmstudio/models/lmstudio-community/Qwen2.5-Coder-7B-Instruct-MLX-4bit"
```

The results already computed need no model; `--reevaluar NOMBRE` recomputes the metrics from the detail file.

## Files

- `generar_pares.py`: templates, validation in PostgreSQL and the 80/20 split.
- `preparar_lora.py`: the training format for mlx-lm.
- `evaluar_sql.py`: generates SQL and compares execution and results. Options `--reglas`, `--rag`, `--reevaluar`.
- `rag_reglas.py`: rule selection by keyword.
- `estadistica.py`: Wilson intervals and McNemar tests.
- `reglas_legado.md`: the business rules the model must apply (in Spanish; part of the prompt).
- `data/`: training, evaluation and rejected pairs, and a summary.
- `resultados/`: the detail and summary of each run.
- `adapters/`: the LoRA weights. **Ignored by git**; regenerated with `mlx_lm.lora`.
